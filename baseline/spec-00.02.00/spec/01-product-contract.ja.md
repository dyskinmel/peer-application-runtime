# 01 — プロダクト契約・品質の定義

版 **00.02.00** / 2026-09-05 / **規範候補・未凍結**

正本の位置付けと優先規則は [仕様案内](../START_HERE.ja.md)。本書の規範要件は `catalog/requirements.json`、受け入れ契約は `catalog/acceptance-tests.json` に対応する。

## 1. 製品の約束

PARは、アプリ参加者の端末群で、権限付きデータ共有・ローカル操作・時間をまたぐ受渡し・復旧を成立させる組み込み基盤である。クラウドアカウント、APIキー、特定企業の認証・relay・課金サービスを基本動作の前提としない。完成基準は機能数ではなく、壊れた通信・中断・更新・鍵の紛失に対しても誤った成功を表示しないこと。

「最高水準」は現時点での市場優位性を主張する語ではない。本仕様では、検証可能な安全性、データ可搬性、導入容易性、アクセシビリティ、運用可能性、資源効率を同時に引き上げる開発目標とする。

## 2. 利用者と仕事

| 利用者 | 仕事 | 成功の意味 |
|---|---|---|
| アプリ開発者 | ローカルに作ったアプリを共有可能にする | サーバー実装なしで招待、編集、状態表示、復旧を統合 |
| エンドユーザー | 複数端末・チームで安心して使う | 通信不在でも編集でき、保存場所と未保護分が分かる |
| Keeper提供者 | 指定グループへ余力を提供 | 容量・帯域・電力を制御し、内容を読まずに協力 |
| 運用担当 | 接続・容量・鍵・移行の障害を診断 | 機密内容を収集せず原因と次の操作を判断 |
| OSS contributor | 別host・言語・UIを実装する | 公開契約とfixtureで互換性を判定できる |

最初の参照アプリは共有ノート＋添付ファイル。次の実証アプリはチームチャットと共有タスクリスト。ノート固有のfieldをruntimeへ埋め込まない。

## 3. 品質軸

正当性、機密性・認可、復旧性、可搬性、接続性、説明可能性、操作容易性、資源効率、更新可能性の9軸で評価する。ネットワークがないときの不達を隠すより、保存済みの編集を維持し原因を示す。

| 語 | 正確な意味 |
|---|---|
| local committed | 指定storage classの原子的保存が完了 |
| retained | Keeperが特定rootのbytesを保管したと署名で表明 |
| recoverable at frontier | 対象利用者の鍵・認可と必要data closureを確認 |
| available now | 今回の取得要求またはfresh challengeに応答 |
| caught up | 特定peerが広告した特定frontierに追いついた |
| production-qualified | 公開したprofile・版・環境・障害範囲のgateを通過 |

これらの状態は並列に存在する。たとえばlocal committed=true、remote copies=0、auth freshness=unconfirmedは正常な状態の組合せ。

## 4. プロファイル

`participants-only`は参加者の経路だけを使用。`community-assisted`は参加者が提供するKeeper/Relayを選び、常時稼働性を高める。`external-assisted`は明示登録した第三者サービスを使う。全て同じdata/auth契約を使い、設定変更の前後でegress manifestを表示する。

ここで外部依存を禁じる対象はPARが選ぶサービス。OS、回線、ユーザー指定DNS、アプリ配布経路の存在まで否定しない。SDK内蔵のanalytics、公開STUN、DNS bootstrap、クラッシュ送信などは例外扱いせず、全て外部依存として列挙する。

## 5. 到達点と非保証

正式版の核は招待制Space、Documents、Blobs、Events、Presence、登録済みRPC、Keeper、Recovery、診断とUI部品。Public write network、匿名保管市場、金融的な全体合意、任意コード実行は追加の保証モデルを要する拡張であり、この核へ無理に混ぜない。

参加者全員が停止しコピーへの時間的経路もない場合は配送できない。過去の平文の回収、世界全体の最新状態の証明、端末数から独立した人間の数の証明、悪意あるownerからの保護は保証しない。これらは機能不足の言い訳ではなく、製品表示にも残す境界。

## 6. 本版の位置付け

00.01.00の原則は継承するが、wire互換は主張しない。authority rotation、control sequenceとcontent epochの分離、復旧資格の事前準備、soft limitとhard validityの分離、UI headless契約を追加する。詳しくは `review/CHANGELOG.ja.md`。

規範本文を実装の都合で黙って変更しない。設計変更は差分・理由・影響するtest IDを記録し、破壊的変更は新profileへ移す。

## 規範要件と受け入れ契約

以下のMUSTは本候補仕様内の必須契約。採用候補であり、実装済み・検証済みという意味ではない。詳細な手順・前提は本書本文と対応する試験契約を併読する。

<a id="PAR-CORE-001"></a>
### PAR-CORE-001 — 中央依存の排除
**MUST:** SDKと参照アプリは、設定外のbootstrap・relay・telemetry・認証サービスへ通信してはならない。
受け入れ: `AT-CORE-001` / 最初の必須gate: `G2`。

<a id="PAR-CORE-002"></a>
### PAR-CORE-002 — ローカル優先
**MUST:** 起動と既存データの読書きは、他peerの接続完了を待たず利用可能とする。
受け入れ: `AT-CORE-002` / 最初の必須gate: `G1`。

<a id="PAR-CORE-003"></a>
### PAR-CORE-003 — 保証の区別
**MUST:** local保存・他端末保管・適用・取得・認可鮮度を別の機械可読状態で公開する。
受け入れ: `AT-CORE-003` / 最初の必須gate: `G1`。

<a id="PAR-CORE-004"></a>
### PAR-CORE-004 — 資源同意
**MUST:** 他人向けの保管・中継・RPCは機能別の明示同意と上限設定を必要とする。
受け入れ: `AT-CORE-004` / 最初の必須gate: `G3`。

<a id="PAR-CORE-005"></a>
### PAR-CORE-005 — 可搬性
**MUST:** 認可されたデータと復旧資料を公開形式で取り出せ、運営者の承認なく第三者実装へ移行できる設計とする。
受け入れ: `AT-CORE-005` / 最初の必須gate: `G3`。

<a id="PAR-CORE-006"></a>
### PAR-CORE-006 — 主張の限定
**MUST:** 対応表示はversion、profile、機能、環境、残る制約に結び付け、未実行gateを合格扱いしない。
受け入れ: `AT-CORE-006` / 最初の必須gate: `G11`。
